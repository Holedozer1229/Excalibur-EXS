# GF-03: Proof of work and difficulty adjustment

| Field | Value |
|-------|-------|
| BIP | GF-03 |
| Title | Proof of work and difficulty adjustment |
| Author | Travis Dale Jones |
| Status | Active |
| Created | 2026-09-21 |

## Abstract

SHA-256d proof of work with a 600-second target and 2016-block retarget
window, following Bitcoin's adjustment math — but with a new launch
difficulty, a sliding (per-block) retarget window instead of fixed
boundaries, and a documented v1 byte-order quirk in the PoW comparison.

## Motivation

Bitcoin's `0x1d00ffff` launch difficulty would make a new chain
unmineable; the fork launches at a difficulty a small miner can actually
find blocks at, then lets the retarget find equilibrium.

## Specification

1. **Algorithm**: double-SHA-256 of the 80-byte header, as in Bitcoin.
2. **PoW comparison (persisted v1 behavior)**: a block is valid iff
   `int.from_bytes(sha256d(header), "big") <= target`. Note: this reads
   the raw digest as a big-endian integer, whereas Bitcoin conventionally
   compares the reversed (display-order) digest. The miner stores the
   reversed digest as the block hash. This orientation is a consensus
   rule of v1 — do not "fix" it without a coordinated upgrade, or
   existing blocks become invalid.
3. **Initial difficulty**:
   - mainnet: `0x1e100000` (target exactly 2²³⁶)
   - testnet: `0x1f010000` (target exactly 2²⁴⁰)
4. **Retarget schedule**: heights 1–2016 use the initial bits. The first
   retarget is computed at height 2017 from the timespan of blocks 1–2016.
5. **Retarget window (differs from Bitcoin)**: at every height above
   2016, the adjustment uses a *sliding* 2016-block window —
   `timespan = time[height-1] - time[height-2016]` — rather than fixed
   2016-block boundaries. The adjustment math is otherwise Bitcoin's:
   `new_target = prev_target * clamp(timespan, 1/4, 4×) / (600 × 2016)`.
6. **Clamp**: timespan is clamped to [302400 s, 4838400 s] (¼× to 4× of
   the 1209600 s window), as in Bitcoin.

## Rationale

The sliding window smooths difficulty continuously instead of stepping
every 2016 blocks; on a young chain with volatile hashrate this avoids
long stuck periods after a hashrate drop. The cost is a mild deviation
from Bitcoin's exact retarget cadence — acceptable for a new chain,
documented here so no one mistakes it for a bug.

## Reference implementation

`genesis_fork.py`: `required_bits()` (lines cover the `height <= 2016`
initial-bits rule, the sliding window, and the clamp),
`validate_block()` (big-endian PoW comparison), `target_to_bits()` /
`bits_to_target()` (verified round-trip: `bits_to_target(0x1e100000) ==
2**236`).

## Test vectors

- `target_to_bits(2**236) == 0x1e100000`; `bits_to_target(0x1e100000) == 2**236`
- Mainnet blocks 1–4 (live chaindata) all carry bits `0x1e100000`.
- Block 1: hash `6bb8e3044a7d4974…`, nonce 60007, satisfies the
  big-endian comparison against target 2²³⁶.
