# GF-10: Replay protection and divergence

| Field | Value |
|-------|-------|
| BIP | GF-10 |
| Title | Replay protection and divergence |
| Author | Travis Dale Jones |
| Status | Active |
| Created | 2026-09-21 |

## Abstract

No explicit replay protection is required: the only block the fork
shares with Bitcoin is the genesis block, whose coinbase is unspendable
on both chains. No spendable history is shared, so no transaction can
replay. Divergence from Bitcoin is proven, not asserted: a fork node
rejects Bitcoin's block 1.

## Motivation

Replay protection is mandatory when a fork shares spendable UTXOs with
its parent (the usual case). Here the shared history is exactly one
unspendable coinbase, so the protection is structural rather than
cryptographic — and the divergence is demonstrated by validation, not
by slogan.

## Specification

1. The fork and Bitcoin share precisely one block: the genesis block
   (GF-02).
2. The genesis coinbase is unspendable on both chains (Bitcoin consensus;
   the fork never creates a spend path for it).
3. Therefore the set of spendable UTXOs shared between the chains is
   empty, and no transaction valid on one chain can be replayed on the
   other.
4. No sighash fork-id, no replay-protection opcode, no address-format
   quarantine is required beyond the distinct network parameters
   (GF-01).
5. **Divergence proof (measured)**: Bitcoin's real block 1 used
   `nBits = 0x1d00ffff`. The fork requires `0x1e100000` at height 1
   (GF-03), so a fork node rejects Bitcoin's block 1 with
   `bits 0x1d00ffff != required 0x1e100000`. Same parent (genesis),
   different child, different rules: a hard fork at genesis.

## Rationale

Adding replay-protection machinery where no replay is possible would be
theater. The honest design states the structural fact and proves the
divergence by running the validator against Bitcoin's real block 1.

## Reference implementation

`genesis_fork.py`: demo step [4] runs `validate_block()` on Bitcoin's
block-1 header fields and records the rejection; `FORK_SPEC.md`
documents the measured divergence.

## Test vectors

- Bitcoin block 1 header (`bits 0x1d00ffff`, prev = genesis hash) →
  `validate_block` returns `["bits 0x1d00ffff != required 0x1e100000",
  ...]` on the fork's mainnet params.
